# 我的学习经历笔记

交付一种能让笔记主人想起“当时我为什么困惑、怎么理解、实际做过什么”的笔记。真实经历是依据，个人视角是表达，连贯主线是组织方式，快速回忆是检验标准。内容准确、熟悉亲近，不以教材式百科覆盖替代个人学习过程。

## 一、先确定证据与归属

- 使用当前对话、用户提供的作答与截图，以及与任务直接相关的现有笔记。先读目标知识库的规则、目录和相关条目，再决定归档位置；不为凑经历扩展检索私人历史。
- 区分四类材料：用户原话或实际行为、教师或资料的内容、整理者的解释、尚未证实的推断。引号只用于能核对的原话；改写注明是归纳，不冒充原话。
- 用户问过、答过、改过、运行过、放弃过或主动暂缓过的关键环节都可记录。不虚构情绪、动机、进步、分数、日期和“我终于理解了”等个人结论。
- 素材不足时先整理有证据的部分，必要处注明“本次无记录”，只对实质缺口提问。跨日交流区分发生日期与整理日期，不把整段历史写成今天发生。
- 根据知识依赖归档，而非仅按正在看的课程命名。例如为数据结构补 C 语法，应进入可找到的课前基础条目，正文只留联系与入口。复用现有条目，不默认另建学科顶层目录。

## 二、先串主线，再决定有几篇

成文前先用几句话回答：我起初想解决什么？为什么卡住？为此补了什么？哪个例子或行动改变了认识？现在能做到什么、还有什么没做到？这构成整组笔记的学习主线。

同时区分两种顺序：学习经历按实际发生或明确的阶段展开；概念讲解按必要的前置知识展开。不为让故事顺滑而篡改经历次序。

- 默认先写一篇能从头读到尾的主线笔记。只有某个概念已有独立复习价值、现有条目需要复用，或篇幅确实阻碍阅读时，才拆出专题。
- 每个完整解释、详细纠错、例子指定一个正文归属。其他页面只用一句上下文加精确链接，不复制整段。主线中的简短经历摘要可以保留。
- 索引负责找路，主线负责理解为何学到这里，专题负责解释清楚。短任务可合在一篇，不强制建立三种页面，更不固定生成八篇等数量。
- 主线的相邻段落写明过渡原因，例如“要接收结果，先得分清变量保存的值；要理解指针，再把值与地址分开”。只罗列链接不能算串联。
- 专题入口说明它解决主线中的哪个疑问；结尾用一句话说明它让下一步成为可能，并链接确实相关的下一条目。分支可回到主线，不强行把所有知识拼成直线。
- 正文只保留推动理解的关键经历。环境详情、长代码、原始题目与补充边界按需放入专题、折叠区或附件，不把所有材料平铺为同等重点。

涉及多篇笔记、已有内容显得零散或需要示例时，阅读 [references/coherent-structure.md](references/coherent-structure.md)。

## 三、从学习者视角保留理解变化

以有证据的“我当时……”为入口，接上具体问题与修正。亲近感来自熟悉的原话、做过的例子和真实犹豫，不来自添加口号、戏剧性独白或鼓励套话。

一处重要转折通常包含：原先怎么想 → 这一想法具体错在哪里或缺什么 → 哪个解释、对照或操作帮助区分 → 现在的准确理解 → 掌握证据与剩余缺口。按材料取舍，不机械地把每段填成五栏。

- 避免把错误归结为“基础差”。写到具体混淆，例如“把指针自身的地址与其保存的地址交换了”。
- 未经修正的错误不能单独留在正文。错误标红且标注“原误解／原答案”，紧接正确解释；颜色不是唯一信号。
- Obsidian 可使用 `<span style="color:#ff6b6b;">原误解：……</span>`；检查主题下的可读性。若目标格式不支持 HTML，使用它原生的红色字体或错误提示块，不把原始标签交给读者。
- 局部或有条件正确的想法标为“需要细化”，不要整段染红宣判全错。不要擅自把用户没说过的话记为其错误。
- 题目、用户作答、批改和后续补练有明确对应。保留有意义的原分数并说明依据；不补造评分或把一次填空正确升级为独立掌握。
- 待学、能跟随解释、能辨认、能补全、能独立写、已运行验证等状态要有相应证据。整理者自动运行通过与用户亲手运行分开写；没有证据时不强行给能力评级。
- 用户主动暂缓的难点明确标为“暂按固定写法使用，后续回看”，不为显得完整追加一大段更难的知识。

## 四、用熟悉场景与图形降低抽象程度

- 优先沿用用户或老师已采用的同一问题场景，一次只改变一个需求或概念。新场景会增加理解负担时不随意换题。
- 图形回答一个具体混淆：位置与内容、传入与返回、修改自身与修改所指对象、步骤前后发生何种变化。标清变量、值、地址、箭头和必要假设；不要只有漂亮盒子。
- 有状态变化时尽量保留同一布局作前后对照，明确哪些量变化、哪些不变。类比注明边界，不能暗示不存在的内存布局或物理比例。
- 选目标笔记工具真正能显示的形式：简单关系可用文本图；复杂关系再用兼容的图示或本地图片。图片放知识库长期附件目录并嵌入，不只引用临时文件。
- 图旁写出一句结论；格式表、检查清单可辅助速查，不与正文重复讲一遍。没有降低理解成本的图表不添加。

## 五、交付前做结构与事实检查

验收不只看“内容全不全”，还看能否沿主线读通：

1. 开头能否快速看出学习起点、核心转折、当前状态？每个主要段落为何出现在这里是否明确？
2. 能否用用户记得的那句话找到专题？每个新增专题有无入口，读完能否知道回到哪里？
3. 是否有同一知识点多处完整讲解、反复贴代码、过多分支或为模板凑内容？合并重复，以链接替代副本。
4. 错误是否醒目且旁边有修正？“尚不理解”“暂不深究”是否被如实保留？技术解释与类比是否准确？
5. 链接、章节锚点、图片路径与渲染是否有效？条件允许时检查实际阅读视图，特别是红字、代码、表格和插图。不要为查排版无故安装插件或改全局外观。
6. 有完整代码、计算或可验证结论时，做与风险相称的验证；错误示例与不可独立运行的片段明确标记。说明自动检查与本人实践的边界。

完成后简短给出主线入口、归档位置、重要验证与剩余缺口。尊重知识库已有命名方式；不自动创建 MEMORY.md，也不把笔记整理解释为全局记忆写入授权。

## 六、后续优化这个 skill

收到真实使用反馈时，先定位是证据、叙事、知识归属、篇幅还是导航的问题，再在用户授权的 skill 修改任务中精准调整相应规则或参考示例。不自动回写其他笔记，不为一个案例不断增加通用强制步骤。

改结构时同时核对入口与参考文档，保留互相一致的一处规则来源；用相关的新案例检查是否改善了连贯性且未损害真实性。没有比较过的效果，不声称已经解决所有杂乱问题。
